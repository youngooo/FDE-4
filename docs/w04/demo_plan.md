# Demo 方案

## 链路与选择理由

- **所选链路**：月度会员复购率查询与数据来源覆盖说明。主指标 `monthly_repeat_rate`（月内复购率），配套 `monthly_buyer_count`（月内购买会员数）与 `monthly_repeat_buyer_count`（月内复购会员数），模型为 `monthly_member_activity`（会员 × 自然月的有效订单数）。
- **服务哪项会员运营工作**：会员复购运营。沈总在群里要求「下周例会看能跑起来的东西，最好跟会员复购有关」，本链路直接回答「某月/某几个月会员复购率是多少」，是例会最想先看到的数字。
- **为什么先验证这条链路**：
  1. 复购是本周数据能直接支撑的问题——订单覆盖 2024-09-01 至 2026-09-01（不含），按月聚合即可得到月内复购，38 项指标中该指标定义完整、可执行。
  2. 复购天然依赖「同一会员在同一自然月内多单」，正好把「部分覆盖」暴露出来：旧收银系统消费记录未导出时，月内复购会被低估，回答必须限定结论范围。
  3. 月度口径固定（只支持完整自然月、全门店），边界清楚，便于检查回答有没有把未知当零或一律拒答。
- **为什么先做单月、再看多月**：单月（2026年8月）能最小验证 intent→SQL→answer 全链路与口径；多月（2025年9月—2026年8月，12 个整月）能验证按月分组与覆盖边界表达。两者都跑通后，再用同一个问题做覆盖说明的调优。

## 数据可用性、最小验证与已有证据

- **用到的数据**（导入后的青禾库，`.runtime/w04/run-01/project-c`，数据版本 `qinghe-w04-v1.1`）：清洗后的 `orders.csv`（读入 168,253，接受 167,661，隔离 256，去重 336）、`members.csv`（119,751 / 隔离 3）、`stores.csv`（403）、`cards.csv`（16,349 / 隔离 299）；衍生模型 `monthly_member_activity`。
- **覆盖到哪里**：coverage=`[2024-09-01, 2026-09-01)`（结束日不含），reference_date=`2026-09-01`，时区 `Asia/Shanghai`；来源只含新 CRM 导出的会员、订单、会员卡、门店四个文件，旧收银系统消费记录未导出，小林工作账只用于对照核查、不导入查询库。
- **有哪些异常**：订单隔离 256 条（超额退款、无效日期等）、会员隔离 3 条、会员卡隔离 299 条，均不进查询库；回答里必须说明这些记录未计入。
- **结果能否追溯**：每次运行都落在 `artifacts/w04/demo_runs/run-XX/<trace_id>/`，含 `result.json`（问题、回答、状态）、`query_result.json`（SQL 与 rows）、`dataset_snapshot.json`（当时数据集的 coverage_notes）、`intent-trace.json` / `answer-trace.json`。SQL 可重放到同一 project。
- **最小验证链路**：一个完整自然月 + 一个指标 + 一次三段式调用。run-01 得到 2026年8月月内复购率 **11.80%**（`0.11803398501735794`），SQL 为按 `monthly_member_activity` 统计「有效订单数≥2 的会员数 ÷ 有效订单数≥1 的会员数」，见 run-01 的 `query_result.json`。
- **已有证据**：
  - run-01（2026年8月单月，调优前）→ ok，11.80%；
  - run-06（2025年9月—2026年8月 12 个整月按月展示）→ ok，16.73% 一路降到 11.80%，回答已带覆盖说明；
  - run-07（与 run-01 同题，改回答提示词后）→ ok，11.80%，回答明确声明数据来源与时间覆盖边界。

## 暂不覆盖范围与待验证条件

- **这次不覆盖什么**：
  - **时间**：2026-09-01 及之后（含 2026年9月整月、2026-09-01 当日）无数据；2024-09-01 之前无数据。
  - **来源**：旧收银系统消费记录未导出，会员在旧系统的消费看不到，月内复购可能被低估；跨系统自然人是否同一人未做归一。
  - **记录**：被隔离的订单 256 / 会员 3 / 会员卡 299 条未计入；小林工作账（回访名单 301、勿扰名单 121）只用于对照，不在查询库。
  - **能力**：`monthly_*` 只支持完整自然月、全门店口径，非整月窗口与门店/区域维度复购未在本 demo 验证。
- **什么条件满足才能扩大**：
  - 要在覆盖范围外下整体经营结论，需先补导旧收银系统消费记录并完成跨系统会员归一；
  - 要做门店/区域维度复购，需指标库确认 `monthly_*` 是否放开维度限制并复测；
  - 要覆盖 2026年9月，需下一版导出把该月纳入；
  - 要让「部分覆盖窗口」直接给出已覆盖部分的结果，需先定协议层的部分覆盖语义（见下一节 bad case 2）。

## 判断说明：关键假设及继续、缩小范围、调整方向的条件

- **关键假设**：
  1. 月内复购率 = 同一自然月内有效订单数 ≥ 2 的会员账户数 ÷ 该月有效订单数 ≥ 1 的会员账户数，按月、全门店汇总（来自 W03 指标定义与老周、小林访谈）。
  2. 订单表能代表会员真实购买行为，但只限新 CRM 已导出的部分；旧收银系统消费记录的缺失会影响复购被低估的程度。
  3. 参考日 2026-09-01 之前数据完整，该日及之后不含。
- **最小验证链路与选择依据**：先用单月（run-01）验证 intent→SQL→answer 全链路与口径；再用 12 个整月（run-06）验证按月分组与边界表达；最后用同题前后对照（run-01 → run-07）验证覆盖说明能被回答采纳。选这条是因为它用最少的数据与一次调用即可判定链路是否可用，且口径固定、边界清楚。
- **已有证据与待验证条件**：已有 run-01 / run-06 / run-07 的成功证据，能证明链路可用且覆盖说明可被采纳；待验证的是「请求部分落在覆盖范围内」时的处理，以及门店维度复购能力。后者将作为上一节的讨论项带入下一轮验证。
- **继续的条件**（满足即继续扩指标）：月内复购率的月度趋势与业务方观察不矛盾，且回答中稳定出现数据来源与覆盖边界说明。
- **缩小范围的条件**（满足则先只做部分结论）：若与老周核对后确认旧收银系统消费记录的缺失会让月内复购被明显低估，则先只在新 CRM 覆盖范围内做趋势对比，对外不称「全公司复购率」，并注明口径。
- **调整方向的条件**（满足则先改能力再扩场景）：若「部分覆盖窗口被整体拒答」（bad case 2）在例会或日常问数中频繁出现，则先改协议与工具层的覆盖裁剪策略与「部分覆盖」语义，再继续扩展指标与维度。
